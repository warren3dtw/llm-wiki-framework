# 框架說明

這份文件說明知識庫的整體設計：有哪些東西、它們怎麼關聯、資料怎麼流動、怎麼決定能不能公開。操作細節在 [`USING.md`](../USING.md) 和 [`MAINTAINING.md`](../MAINTAINING.md)，欄位的正式定義在 [`schema.json`](../schema.json)。

這份文件會跟著空框架一起輸出，所以不寫任何專案或個人的資訊。

## 1. 一句話

把原件（PDF、網頁、工作專案）整理成四種頁，用原子串起來，再把頁打包成 agent 可以照做的技能；全部用純文字和 git 管理，agent 先讀索引再開檔。

```
輸入                     知識庫                              輸出
────                     ──────                              ────
原件 ──ingest──→ 頁（筆記、資料、圖、程式碼）──export──→ 圖集、數據手冊
                          ↑ 依據                 │
工作專案的技能 ─ingest─→ 技能 ──────────export/install──→ 私人版、公開版技能
        ↑                                                      │
        └────────── 在專案裡使用、改進 ←───────────────────────┘
查詢的答案 ──fileback──→ 頁
```

## 2. 有哪些東西

| 東西 | 英文 | 放哪裡 | 是什麼 | 代號 |
|---|---|---|---|---|
| 主題 | wiki | `wikis/<名稱>/` | 一個知識範圍。分通用（general）和專案（project） | 名稱 |
| 原件 | raw | `wikis/<主題>/raw/` | 原始文件和它的登記卡。原件本身不進 git，登記卡和擷取的文字進 git | `<主題>:raw/<代號>` |
| 原子 | atom | `atoms/` | 最小的概念，只有名稱（中、英、日、別名）和上下位關係，沒有內容。全部主題共用 | `atom:<名稱>` |
| 頁 | page | `wikis/<主題>/<類型>/<知識點>/` | 知識的內容，四種：筆記、資料、圖、程式碼 | `<主題>:<類型>/<檔名>` |
| 知識點 | point | 四種頁底下的同名資料夾 | 依知識領域分的一組頁。入口是 `note/<知識點>/NOTE.md` | `<主題>:<知識點>` |
| 項目 | item | 檔名的前段 | `<知識點>-<三位數編號>`。同編號的頁是同一件事的不同形式 | `<知識點>-001` |
| 技能 | skill | `skills/<代號>/` | agent 可以照著做的能力包：何時用、規則、步驟、腳本、驗收題。全部主題共用 | `skill:<代號>` |
| 個人設定 | profile | `skills/<代號>/profiles/<專案主題>/` | 技能在某個專案的慣例、參數、案件經驗 | — |
| 公式 | calc | `calc/<主題>/` | 可執行的公式，依據某一頁，由那一頁的核對區塊驗證 | `calc/<檔>.py::<函式>` |
| 索引 | index | `index/` | 由程式產生，給 agent 先讀 | — |
| 計畫 | plan | `docs/plans/<日期-名稱>/` | 一次做不完的工作：plan、specs、tasks，tasks 有階段與存檔點表 | 資料夾名稱 |
| 框架紀錄 | — | `CHANGELOG.md`、`docs/FEEDBACK.md` | 框架的版本，以及框架本身的問題和調整 | 版本號 |

四種頁是知識的**形式**：

| 頁 | 存什麼 | 附帶檔 |
|---|---|---|
| 筆記 note | 用文字講一件事。種類分三組：原理（概念、規則）、做法（步驟、算例）、觀點（主張、審查） | 無。不放數據，連到資料頁 |
| 資料 data | 所有數據 | 同名 `.csv` |
| 圖 figure | 影像，加上圖上原文和說明 | 影像檔 |
| 程式碼 code | 程式片段、設定檔、提示詞 | 程式檔 |

技能不是第五種頁。頁回答「這是什麼、為什麼」，技能回答「這件工作怎麼做」，而且技能要能離開知識庫、裝到別的地方用。

## 3. 怎麼關聯

```
原件 ◄──raw── 頁 ──atoms──► 原子 ◄──kind-of / part-of── 原子
              │ ▲
   pair（同編號）│ │ from、data、against、see_also
              ▼ │
              頁
              ▲
              │ from（依據）        points（用到的知識點）
            技能 ──────────────────────────────► 知識點
              │ uses                    atoms
              ▼                      ──────────► 原子
            技能
              │ profiles/<專案主題>/
              ▼
          專案主題的頁
```

| 欄位 | 誰可以寫 | 指向 | 意思 | 對方改了以後 |
|---|---|---|---|---|
| `raw` | 頁、技能 | 原件 | 出處和位置 | — |
| `atoms` | 頁、技能 | 原子 | 講到哪些概念。跨語言搜尋靠它 | 不必重看 |
| `point`、`item` | 頁 | — | 所屬的知識點和項目，等於資料夾和檔名 | — |
| `pair` | 頁 | 同編號的頁 | 同一件事的其他形式（例如細部圖和它的配置表） | — |
| `from` | 頁、技能 | 頁 | 依據誰 | **要重看**（lint 會提醒） |
| `data` | 頁 | 資料頁 | 用到哪些數據 | **要重看** |
| `against` | 頁 | 頁 | 反駁或審查誰 | — |
| `see_also` | 頁 | 頁 | 相關，不是依據 | 不必重看 |
| `points` | 技能 | 知識點 | 這件工作用到哪些知識領域 | 不必重看 |
| `uses` | 技能 | 技能 | 要先用哪些技能 | — |
| `kind-of`、`part-of` | 原子 | 原子 | 上下位關係。查上位詞會連下位詞一起找到 | — |

重看之後內容不必改，就在檔頭填 `checked: 日期`，提醒就會消失。

四條方向規則，lint 都會檢查：

1. **通用主題不能引用專案主題**；專案主題可以引用通用主題。欄位、內文連結、`raw` 都算。
2. **技能本體（SKILL.md、scripts/）不能引用專案主題**；只有 `profiles/<專案主題>/` 可以。
3. **編號全部主題共用一套**；同一個編號只屬於一個主題，同一種頁裡只有一頁，同編號的檔名完全相同。
4. **每個知識點在每個主題都有入口檔**，而且列出這個知識點的全部頁。

## 4. 資料怎麼流動

### 4.1 輸入

| 來源 | 指令 | 結果 |
|---|---|---|
| PDF、網頁 | `ingest raw` 登記 → `ingest text`／`find`／`crop` 擷取 → 照 `templates/` 起草頁 → 更新 NOTE.md | 草稿的頁 |
| 查詢得到的答案 | `fileback` | 草稿的頁，`origin: fileback`，`from` 指向依據 |
| 工作專案裡的技能（第一次） | `ingest skill <資料夾>` | `skills/<代號>/`，草稿、私人；另建一張原件登記卡 |
| 工作專案裡改過的技能 | `ingest skill <資料夾>`（有 `.wiki-source`） | `skills/<代號>/incoming/` 裡的差異說明，人工併入 |
| 想法、疑問、發現的錯誤 | 寫進主題的 `inbox.md` | 待處理 |

### 4.2 多次工作

一次做不完的工作（整理一整章、匯入技能、改框架）先用 `new plan` 開計畫：寫目標和驗收條件，再分階段做。每個階段結束或要停時，在 tasks 的存檔點表記產出、commit、lint 結果和下一步；續作從第一個不是「已驗收」的階段接著做。結束後移到 `docs/plans/archive/`。整個任務完成而且 lint 通過才 commit，不自動 push。

這些規則原本是給工作專案用的（技能 init-001 會把它們寫進每個工作專案的 docs），知識庫也照同一套。規則原文附在 `skills/init-001/references/`。

### 4.3 檢查和確認

- `lint` 檢查格式、欄位、連結、編號、配對、入口檔、方向規則、可見度、索引是否最新、計畫資料夾、框架版本，並執行公式的核對區塊和技能的測試。錯誤要修，警告是待辦。
- 新的頁和技能一律是 `draft`。只有擁有者能改成 `reviewed`。
- `query review` 依「先確認被依據的」排序：原件 → 原子 → 資料 → 圖 → 程式碼 → 筆記（原理 → 做法 → 觀點）→ 技能。

### 4.4 使用

- agent 先讀 `index/OVERVIEW.md`，再用 `query` 找頁；不要一開始就掃全部檔案。
- 專案主題預設不查，問題提到專案才查。
- `query trace` 往上追到原件的位置；`query impact` 往下查誰依據它，包含技能。
- 有技能的工作，先讀 SKILL.md 照著做。

### 4.5 輸出

| 指令 | 產物 | 給誰 |
|---|---|---|
| `export atlas`、`export datasheet` | 單一 HTML 的圖集、數據手冊 | 自己 |
| `export skill <代號> --profile <專案主題>` | 私人版技能：附那個專案的 profile 和全部依據 | 自己的工作專案 |
| `export skill <代號> --public` | 公開版技能：profile 換成示範，只附可以公開的依據，輸出前掃描 | 別人 |
| `install skill ...` | 把技能裝進工作專案，留下 `.wiki-source` | 自己的工作專案 |
| `export framework` | 空框架：只有程式、規則、模板和框架的技能 | 別人 |

### 4.6 技能的循環

```
知識庫的技能 ──install──→ 工作專案 ──（工作時直接改，記在專案的 FEEDBACK）──┐
     ▲                                                                    │
     └──人工併入──  incoming/ 的差異說明  ◄──────ingest skill──────────────┘
```

併入時，每一條改動先判斷屬於哪一層：

| 層 | 例子 | 放哪裡 | 能不能公開 |
|---|---|---|---|
| 工具知識 | 某個 API 的行為、腳本寫法 | SKILL.md、scripts/；會重複使用的寫成通用主題的頁 | 可以 |
| 領域知識 | 判斷規則、順序、門檻 | 通用主題的頁，技能 `from` 它 | 看原件的授權 |
| 慣例 | 圖號規則、編號族、圖層命名 | `profiles/<專案主題>/conventions.md`、`config.json` | 要能替換 |
| 案件事實 | 某張圖的錯誤、某次的決定 | `profiles/<專案主題>/cases.md`，或專案主題的頁 | 私人 |

判斷「通用還是個案」：換專案、換電腦、換人仍會發生的才算通用；原因還是推測的先不併入。

## 5. 能不能公開（share）

只有原件要標，其他都用推算的。

| 值 | 意思 |
|---|---|
| `public` | 可以公開 |
| `attribution` | 可以公開，但要標出處並遵守授權條件 |
| `private` | 不能拿出這個 repo |

- 原件沒標的當成 `private`。
- 頁：取它的 `raw` 原件和 `from` 依據裡最嚴格的。專案主題的頁一律 `private`。
- 技能：取它的 `raw`、`from`、`uses` 裡最嚴格的，再和自己標的 `share` 取嚴格的。沒有任何來源的技能（自己寫的）以自己標的為準。
- 頁和技能自己標的 `share` 只能更嚴格。標得比推算寬，lint 報錯。
- 原子是名稱，可以公開；「組織與專案」類的原子是 `private`。

公開輸出有四層防護，由外到內：

1. **預設私有**：沒標的都不輸出。
2. **結構分離**：專案的東西只能放在專案主題和技能的 profiles，輸出時整塊不帶。
3. **行內標記**：拆不開的句子用 `<!-- private -->…<!-- /private -->` 包起來，公開輸出時刪掉。
4. **輸出前掃描**：禁用字（根目錄和各 profile 的 `denylist.txt`）、本機路徑和 Email、和不能公開的原件連續相同的文字。有一項命中就不輸出，並列出檔案和行號。

另外，草稿的技能預設不能公開輸出；加 `--draft` 才會輸出，而且輸出檔會標示草稿。每次輸出都有一份報告，寫明放了什麼、沒放什麼、掃描結果。

## 6. 技能的結構

```
skills/<代號>/
  SKILL.md            本體。檔頭有知識庫用的欄位；輸出時只留 Agent Skills 規格的欄位
  scripts/            腳本。test_*.py 由 lint 執行
  references/         格式定義、補充說明
  tests.md            驗收題：情況、應該、不應該
  CHANGELOG.md        版本紀錄
  profiles/<專案主題>/  conventions.md、config.json、cases.md、denylist.txt
  profile.example/    去識別化的示範
  incoming/           從工作專案帶回來、還沒併入的差異
```

- 代號是「前綴-三位數」，等於資料夾名稱和 `name`，符合 Agent Skills 規格（名稱只用小寫英數和連字號，而且等於資料夾名稱）。
- SKILL.md 本文裡一律寫 `profile/`。知識庫裡一個技能可以有好幾份 profile（一個專案一份）；輸出時選一份放成 `profile/`，公開版用 `profile.example/`。
- SKILL.md 建議 500 行以內，細節放 `references/`。
- 輸出時，`from` 指到的頁會整理成 `references/` 裡的檔案，本文最後加一節對照表；用到的 `calc/` 函式複製到 `scripts/calc/`。

## 7. 指令總覽

全部從 `python scripts/wiki.py <動作>` 進入，只用 Python 標準庫（從 PDF 擷取另需 poppler、tesseract）。

| 動作 | 做什麼 |
|---|---|
| `new wiki`、`new skill`、`new plan` | 建立新的主題、技能、計畫 |
| `ingest raw`／`text`／`page`／`find`／`crop` | 登記原件、擷取文字和圖 |
| `ingest skill` | 從工作專案帶進技能，或帶回改動 |
| `query overview`／`search`／`atom`／`get`／`data`／`figure`／`point` | 找和讀 |
| `query trace`／`impact` | 往上追依據、往下查影響 |
| `query review`／`share` | 待確認清單、可見度 |
| `fileback` | 把答案存回成一頁 |
| `index` | 重建索引 |
| `lint` | 檢查，並執行公式核對和技能測試 |
| `export atlas`／`datasheet`／`skill`／`framework` | 輸出 |
| `install skill` | 把技能裝進工作專案 |

## 8. 從空框架開始

1. `python scripts/wiki.py new wiki <名稱> --kind general` 建立第一個主題。
2. 原件放進 `wikis/<名稱>/raw/`，`ingest raw` 登記，填好授權和 `share`。
3. 照 `templates/` 起草頁，更新 NOTE.md。整理一整份原件這種一次做不完的工作，先 `new plan` 開計畫。
4. `python scripts/wiki.py index`，再 `lint`，零錯誤才算完成。
5. 要建立工作專案時，用技能 `init-001`。
6. 要把工作方法留下來時，`new skill <代號>`，或用 `ingest skill` 從工作專案帶進來。
7. 根目錄的 `denylist.txt` 填上不能公開的字；`framework.json` 填要帶進空框架的技能和要替換的字。
8. 改了框架本身時，在 `CHANGELOG.md` 加一筆、更新 `schema.json` 的 `framework_version`，問題記在 `docs/FEEDBACK.md`。

## 9. 已知的限制

- 掃描只找得到清單上的字、固定樣式的個人資訊和照抄的原件文字。換句話說的機密、圖片裡的字，掃描找不到；主要還是靠結構分離和預設私有。
- 技能從工作專案帶回來的改動不會自動合併，因為要人判斷每一條屬於哪一層。
- `from` 和 `data` 更新的提醒只比對日期，不知道改動有沒有影響到自己。
- 只能在外部軟體裡跑的腳本沒有自動測試。
- 知識庫是學習筆記，不是設計依據。
